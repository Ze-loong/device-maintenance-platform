# 系统架构与代码导览

> 面向"想快速搞清楚这份代码怎么组织、一条数据从进来到出去经过了哪些文件"的读者——无论是回顾自己写的代码，还是给别人介绍这个项目。业务层面的判断依据（为什么设计成这样）见 [`00-业务设计.md`](00-业务设计.md)，本文档只讲工程实现：目录职责、分层规则、代码级数据流向。

## 一、目录结构总览

```
backend/            后端服务：FastAPI + APScheduler，单进程部署
  app/
    api/             HTTP 路由层（controller）
    mqtt/            MQTT 消息路由层（controller）
    service/         业务逻辑层
    models/          SQLAlchemy ORM 表定义
    repository/      数据库持久化层
    schemas/         Pydantic 数据校验（HTTP 请求/响应、MQTT 上下行）
    ai/              大模型适配（HTTP 客户端、提示词模板、脱敏上下文）
    core/            横切关注点（配置、数据库连接、日志、鉴权、时区工具、业务配置读取）
    tasks/           APScheduler 定时任务注册
    templates/ + static/   管理端页面（Jinja2 + 原生 JS + Chart.js）
    main.py          FastAPI 应用装配入口
  config/            业务配置（设备类型、位置、画像维度等，YAML）
  scripts/           一次性/手动运维脚本（建表、建管理员、重置演示数据）
  tests/             pytest 测试

simulator/           独立的 MQTT 客户端程序，模拟风机网关上报数据（不 import backend 代码）

deploy/              Docker Compose 编排、部署脚本、EMQX 配置

设计文档/            架构与业务设计文档（本文件所在目录）
```

**为什么 `simulator/` 是独立程序而不是 backend 的一部分**：它模拟的是"部署在车间现场、给风机做数据采集的网关设备"，跟平台后端物理上跑在不同机器、属于不同的软件边界。保持代码隔离（不共享 import）是在强制自己遵守这条边界，避免写着写着图方便直接复用 backend 的类型定义，导致边界只存在于文档里、不存在于代码里。

## 二、五层架构图解

`backend/app/` 是标准的分层架构，数据只能单向往下传递（上层依赖下层，下层不知道上层的存在）：

```
┌─────────────────────────────────────────┐
│  controller 层（两个入口，职责相同）        │
│  api/*.py          HTTP 路由              │
│  mqtt/client.py    MQTT 消息路由           │
│  —— 只做：接收、校验格式（用 schemas）、    │
│     调用 service、返回；不写业务规则         │
└──────────────────┬──────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  service 层：业务逻辑                      │
│  event_service / inference_service /      │
│  profile_service / device_service / ...    │
│  —— 归属校验、归档、置信度计算、降级兜底、    │
│     画像生成编排；只依赖 repository/ai/core │
└──────────────────┬──────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  repository 层：持久化                     │
│  每张表一个 repository 类，                │
│  所有 SQL/ORM 查询只在这一层出现            │
└──────────────────┬──────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  models 层：SQLAlchemy ORM 表定义          │
└─────────────────────────────────────────┘

  schemas/    横向支撑：controller 层用它把外部输入（JSON）转成类型安全的 Python 对象
  core/       横向支撑：配置、数据库连接、日志、鉴权，被各层按需引用
  ai/         横向支撑：只被 service 层调用，封装大模型交互细节
```

**这个分层要解决的核心问题**：业务规则（比如"置信度怎么算"、"归属校验的顺序"）只应该存在于一个地方（service 层），不能散落在路由函数或 SQL 查询里——否则同一条业务规则要在多处维护，容易改漏。`api/` 和 `mqtt/` 两个入口分别接收 HTTP 请求和 MQTT 消息，但最终都调用同一个 `event_service.handle_event()`，这保证了"网关真实上报"和"管理端调试面板手动触发"这两条路径的业务行为完全一致，调试的时候不用担心"页面上测试通过了，但真实链路可能不一样"。

## 三、三条核心数据流向

### 1. 上行事件处理链路（设备上报 → 入库 → 实时推理 → 下行回推）

这是系统最核心的一条链路，一次振动告警从设备发出到运维人员收到建议，完整经过：

```
风机网关（simulator）
  │ MQTT publish: line/{line_id}/{device_id}/event
  ▼
app/mqtt/client.py :: MQTTClient.on_message()
  │ 校验报文大小 → Pydantic 解析为 UplinkEvent → 校验 topic 与 payload 里的编号一致
  │ 放入内存队列（不在网络回调线程里做耗时操作）
  ▼
app/mqtt/client.py :: MQTTClient.work()   [独立工作线程]
  │ 从队列取出事件 → 调用 service.handle_event(event)
  ▼
app/service/event_service.py :: EventService.handle_event()
  │ 1. 查 line/device 是否已注册（LineRepository / DeviceRepository）
  │    未注册 → 记一条 unregistered_alert，直接返回兜底预测，不进入后续步骤
  │ 2. 原始报文追加写入 data/raw/{line_id}/{日期}.jsonl（归档，即使是重复消息也留痕）
  │ 3. EventRepository.create_if_not_duplicate() 尝试入库
  │    唯一约束 (device_id, occurred_at, event_type) 命中 → 判定为 QoS1 重复投递，返回 None
  │ 4. 是回填数据（is_backfill=True）→ 只入库，不触发实时推理，直接返回
  │ 5. 是实时事件 → 调用 inference_service.infer()
  ▼
app/service/inference_service.py :: InferenceService.infer()
  │ 1. 按事件的 location + event_type 算出要检索哪些画像维度（get_dimensions_for_event）
  │ 2. ProfileSegmentRepository 检索最近 N 天该产线命中维度的画像分段
  │ 3. 调用 LLMClient.infer()（脱敏后的产线上下文 + 事件关键字段 + 命中的画像片段）
  │    大模型只负责生成 next_behavior / reasoning，不参与置信度判断
  │ 4. calculate_confidence() 用规则代码独立计算 low/medium/high
  │    （告警事件命中天数达标直接 high；常规事件还需匹配画像里的作息时间窗口）
  │ 5. 大模型调用失败 → 捕获 InferenceError，走降级路径：固定兜底文案 + confidence=low
  │ 6. PredictionRepository 落库，返回 DownlinkPrediction
  ▼
app/mqtt/client.py :: MQTTClient.work()（回到调用点）
  │ MQTT publish: line/{line_id}/{device_id}/prediction
  ▼
运维网关订阅 line/+/+/prediction 收到维护建议
```

关键设计点：置信度计算（第4步）不依赖大模型自评，是一段独立于 LLM 调用的规则代码（`inference_service.py::calculate_confidence()`），保证同样的输入无论调用多少次大模型都给出一致的置信度结果。

### 2. REST 调试链路（管理端页面手动触发一次事件）

```
管理端调试页面（templates/debug.html）
  │ HTTP POST
  ▼
app/api/management.py :: debug_predict()（POST /api/debug/predict）
  │ 解析请求体为 UplinkEvent（与 MQTT 入口用同一个 schema）
  ▼
app/service/debug_service.py :: DebugService
  │ 调用与 MQTT 入口完全相同的 event_service.handle_event()
  ▼
（后续步骤与上行链路完全一致）
```

这条链路存在的意义：让开发者不需要真的发一条 MQTT 消息就能测试推理逻辑，同时因为调用的是同一个 `handle_event()`，测试结果对真实链路有效——不会出现"调试页面看起来正常，MQTT 链路却不一样"的情况。`schemas/debug.py` 里对这条链路复用同一去重逻辑的副作用有专门说明（同一时间戳重复调试请求同样会被判定为 QoS1 重投并跳过）。

### 3. 离线画像生成链路（每日定时批处理）

```
APScheduler（app/tasks/scheduler.py）
  │ 北京时间每天 00:30 触发（也支持管理端手动触发单产线或全量重跑）
  ▼
app/service/profile_service.py :: ProfileService.generate_all()
  │ 遍历全部启用中的产线，每条产线独立事务、独立异常处理
  │（单产线失败不影响其他产线继续生成）
  ▼
ProfileService.generate_for_line()
  │ 1. EventRepository 查该产线前一天全部事件
  │ 2. sample_evenly() 等间隔抽样（避免全天事件太多，一次性塞给大模型）
  │ 3. 调用 LLMClient.generate_profile()，模型按五个固定维度
  │    （运行时长规律/振动特征/启停冲击模式/温度趋势/异响异常记录）生成画像正文
  │ 4. 校验模型返回的维度集合"恰好五个、不重不漏"，不满足则整份画像生成失败
  │    （宁可当天画像缺失，也不把半成品写入数据库）
  │ 5. ProfileRepository.upsert() 覆盖写入（同一产线同一天重新生成会覆盖旧画像）
  │ 6. ProfileSegmentRepository.bulk_create() 按维度拆分存入分段表，
  │    供后续实时推理检索用
```

这条链路跟第1条链路是完全独立的两个节奏：一个是事件触发的实时快线，一个是定时批处理的慢线，互不阻塞（详见 `00-业务设计.md` 里的架构设计原则）。

## 四、关键设计点 → 代码位置索引

| 设计点 | 对应代码 |
| --- | --- |
| 置信度三档规则（不靠模型自评） | `app/service/inference_service.py :: calculate_confidence()` |
| 告警事件绕过时间窗口匹配 | `app/service/inference_service.py :: ALERT_EVENT_TYPES` |
| MQTT QoS1 去重 | `app/models/event.py`（唯一约束）+ `app/repository/event_repository.py :: create_if_not_duplicate()` |
| 数据流向大模型前的脱敏 | `app/ai/sanitized_context.py :: SanitizedLineContext` |
| 大模型调用失败的降级兜底 | `app/service/inference_service.py :: infer()` 里的 `except InferenceError` 分支 |
| 数据库故障时的降级兜底 | `app/service/event_service.py :: handle_event()` 里的 `except (SQLAlchemyError, ...)` 分支 |
| MQTT 上下行 topic 粒度设计 | `app/mqtt/client.py :: on_connect()`（订阅）+ `work()`（发布） |
| 定时画像生成 | `app/tasks/scheduler.py` + `app/service/profile_service.py` |
| 业务配置（设备类型/位置/画像维度） | `backend/config/base_data.yaml` + `app/core/base_data.py` |

## 五、如果要重新读一遍代码，建议顺序

1. `app/main.py` —— 看应用启动时装配了哪些组件，建立整体轮廓
2. `app/mqtt/client.py` —— 上行链路的入口，理解队列+工作线程的设计
3. `app/service/event_service.py` → `app/service/inference_service.py` —— 核心业务链路
4. `app/models/event.py` + `app/repository/event_repository.py` —— 去重约束的完整实现
5. `app/ai/llm_client.py` + `app/ai/prompts.py` —— 大模型调用细节
6. `app/service/profile_service.py` + `app/tasks/scheduler.py` —— 离线画像链路
