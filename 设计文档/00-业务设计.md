# 设备预测性维护平台 — 业务设计文档

> 先把业务实体定义清楚，再动代码，避免代码改到一半发现业务逻辑想岔了要返工。

## 一、场景定位

工业风机（车间通风机/冷却塔风机类）的健康度监测与预测性维护平台。风机联网上报运行数据 → 平台校验/归档/入库 → 每日定时用大模型为每台风机生成健康度画像 → 新事件到来时结合画像实时推理"设备是否需要维护"（带置信度与推理依据）→ 平台向运维人员/网关推送维护建议。从零数据冷启动，置信度随数据积累提升。

## 二、业务实体设计

| 实体 | 说明 |
|---|---|
| line（产线） | 平台管理的最小组织单位，一条产线下挂若干台设备 |
| device（风机） | 具体的传感设备，归属某条产线，含设备类型、安装位置 |
| profile（设备健康度画像） | 按设备维度定期生成的健康度画像，分维度存储 |
| event（振动/温度/启停事件） | 设备上报的结构化事件，`event_type` 枚举区分事件性质 |
| prediction（维护建议预测） | 结合画像做出的实时推理结果，含置信度与推理依据 |

## 三、五维传感器画像方案

| 画像维度 | 判断依据 |
|---|---|
| 运行时长规律 | 每日/每班次累计运行小时数、启停次数——判断累积磨损进度 |
| 振动特征 | 加速度/速度值，判断轴承磨损、转子不平衡、不对中 |
| 启停冲击模式 | 短时间内频繁启停对设备寿命的影响 |
| 温度趋势 | 轴承温度、绕组温度，持续上升判断散热/负载异常 |
| 异响/异常记录 | 人工巡检记录或声学传感器捕捉的异常声音，作为振动数据的补充验证 |

## 四、事件类型设计

MQTT 协议采用"`event_type` 粗分类 + `value` 数值字段"的组合设计：`event_type` 只负责区分"这是哪种事件"，具体数值（振动幅值多少、温度多少、启停次数多少）都装在通用的 `value` 字段里，不需要每种读数单独开一个事件类型，这样协议更省字段、扩展更灵活。

实际协议（`app/schemas/mqtt.py` 的 `EventType`，5选一）：
- `fan_started`（风机启动）——触发实时推理快线，记录启停冲击次数
- `fan_stopped`（风机停机）——触发快线，区分正常停机/异常跳停由 `value`/`extra` 字段承载
- `sensor_reading`（振动/温度周期读数）——触发快线，一条消息一个数值，累计多条可在慢线画像生成时形成"全天时序"效果
- `vibration_alert`（振动阈值超限）——触发快线，直接命中"振动特征"维度，不经过位置检索规则表
- `temperature_alert`（温度阈值超限）——触发快线，直接命中"温度趋势"维度，不经过位置检索规则表

设计过程中曾考虑按业务直觉拆出更细的事件分类（比如"设备状态变化"这类通用标签），但实现时发现这类模糊语义无法唯一对应具体的画像维度和故障判断依据——两种超限事件（振动/温度）触发的画像维度和故障模式判断依据不同，必须分开表达，因此最终收敛为上面5类、边界清晰、各自唯一对应处理逻辑的协议设计，没有为了看起来完整而过度设计。

批量画像生成（`profile_service` 慢线每日汇总）不是独立的事件类型，而是把当天全部 `sensor_reading` 等事件按时间顺序抽样后喂给大模型生成画像——"全天时序数据""累计运行时长""启停次数统计"这些统计口径，都是从上面5类事件按天聚合算出来的，不是协议层面的独立事件类型。

## 五、故障模式定义

| 故障模式 | 判断特征 |
|---|---|
| 轴承磨损 | 振动幅值持续上升 + 轴承温度同步上升 |
| 转子不平衡 | 振动幅值突增但温度正常（简化表述，不涉及具体频谱分析细节） |
| 散热不良 | 温度持续上升但振动正常 |
| 联轴器不对中 | 振动+异响同时出现 |

## 六、MQTT Topic 设计

- 上行 `line_id + device_id`（精确定位哪条产线哪台风机上报的振动/温度事件），平台订阅一次即可收全部产线全部风机的事件
- 下行 `line_id + device_id`（**到设备级**）——维护建议的判断标准是"下行内容的实际作用对象"：维护建议本质是单设备行为（"这台风机需要检修"），必须精确路由到目标设备，产线级的粗粒度会让运维人员无法定位具体是哪台设备出了问题

## 七、置信度三档的工业场景表述

置信度分三档，由规则程序计算（不是大模型自评，避免同样输入不同次给出不一致判断）：

| 档位 | 命中画像天数 | 工业场景含义 | reasoning示例 |
|---|---|---|---|
| low（冷启动） | 0天 | 该风机暂无历史运行画像，仅凭通用振动阈值判断 | "暂无历史健康度画像，基于通用振动阈值判断" |
| medium（积累中） | 1-2天 | 命中该设备近期画像分段，结合历史趋势判断 | "近1天振动画像显示轴承温度已有上升趋势，本次振动异常可能与此相关" |
| high（规律稳定） | ≥3天且时间吻合 / 告警事件命中天数达标 | 当前异常与画像记录的磨损趋势高度吻合；或振动/温度超限信号本身已经足够强 | "过去3天该设备振动幅值持续攀升且与本次异常趋势一致，判断为轴承磨损进展" |

**告警事件（`vibration_alert`/`temperature_alert`）的置信度判断依据跟常规事件不同**：常规事件靠"当前时刻是否匹配画像记录的作息规律（时间窗口）"判断，但超限信号本身已经足够强，不需要作息规律佐证——因此告警事件单独放宽为"命中天数达标即可 high"，不要求时间窗口匹配。这个差异化处理是在真实端到端验收时发现并修正的，详见项目根目录的执行记录。

## 八、架构设计原则

`controller → service → models → repository → schemas` 五层架构，外加 `core`（配置/日志/异常）、`ai`（大模型适配）、`tasks`（定时任务）横切层。REST 预测调试接口与 MQTT 订阅端必须调用同一个 `event_service.handle_event()`，保证调试链路与生产链路完全一致，不需要额外维护两套代码。

`simulator/` 是独立 MQTT 客户端程序（模拟风机网关），不依赖 backend 代码，保持完全独立。
