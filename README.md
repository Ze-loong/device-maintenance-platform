# 设备预测性维护平台

> 工业风机联网上报运行数据（振动/温度/启停）→ 平台校验/归档/入库 → 每日凌晨用大模型为每台风机生成健康度画像 → 新事件到来时结合画像实时推理"设备是否需要维护"（带置信度与推理依据）→ 经 MQTT 回推给运维网关。从零数据冷启动，置信度随数据积累提升。

个人作品集项目，面向工业风机（车间通风机/冷却塔风机）场景的健康度监测与预测性维护平台。核心设计目标：系统上线第一天没有任何历史数据也必须正常工作，且预测质量要随数据积累肉眼可见地提升——这是本项目区别于"随便接个 MQTT 转发一下"的核心设计点，完整业务设计见 [`设计文档/00-业务设计.md`](设计文档/00-业务设计.md)。

## 核心叙事：从冷启动到高置信度告警

置信度分三档，由规则程序计算（不是大模型自评，避免同样输入不同次给出不一致判断）：

| 阶段 | 命中画像天数 | confidence | 工业场景含义 |
| --- | --- | --- | --- |
| 冷启动 | 0 天 | `low` | 该风机暂无历史健康度画像，仅凭通用振动阈值判断 |
| 数据积累中 | 1-2 天 | `medium` | 命中该设备近期画像分段，结合历史趋势判断 |
| 规律稳定 | ≥3 天且时间吻合 | `high` | 当前异常与画像记录的磨损趋势高度吻合 |

真实验证：独立触发一次振动/温度事件，冷启动状态下 2.134 秒收到 `confidence=low`；用历史数据生成三天健康度画像后，同一台设备的振动读数事件提升到 `confidence=medium`，**振动超限告警（`vibration_alert`）在三天画像积累后收到 `confidence=high`**——全程真实 DeepSeek 模型、真实 MQTT 链路、真实 PostgreSQL，没有 Mock。

这条链路里有一个不那么显然的设计点：**告警事件（振动/温度超限）的置信度判断依据跟常规行为预测不是一回事**。常规事件靠"当前时刻是否匹配画像记录的作息规律"判断，但"设备振动超限"这个信号本身已经足够强，不需要作息规律佐证——这个判断差异、以及开发过程中因此发现的两个真实设计缺口，详见文末[开发过程中发现并修复的两个真实问题](#开发过程中发现并修复的两个真实问题)。

## 架构

后端采用 `controller → service → models → repository → schemas` 五层架构，外加 `core`（配置/日志/异常）、`ai`（大模型适配）、`tasks`（定时任务）横切层。三条链路：

- **上行链路**：风机网关/模拟器发布事件（`line/{line_id}/{device_id}/event`）→ EMQX Broker → `mqtt/subscriber.py`（controller）解析 → `event_service.handle_event()` 统一入口 → 归属校验 / 原始报文归档 / 结构化入库。
- **推理链路**：事件入库后 → 按规则检索最近 7 天对应维度的健康度画像分段 → 调用大模型（脱敏输入，`SanitizedLineContext` 只含产线编号）→ 置信度规则计算 → 结果入库 → MQTT 回推**到设备级**（`line/{line_id}/{device_id}/prediction`——维护建议本质是"这台设备需要检修"，必须精确到设备才能让运维人员定位目标）。**REST 预测调试页面与 MQTT 订阅端调用同一个 `handle_event()`**，调试链路与生产链路天然一致。
- **离线画像链路**：APScheduler 凌晨定时（或手动触发）→ 汇总前一日事件（超量抽样）→ 调用大模型生成五维度健康度画像（运行时长规律/振动特征/启停冲击模式/温度趋势/异响异常记录）→ 分段存入数据库。

## 技术栈

| 分类 | 选型 | 理由 |
| --- | --- | --- |
| MQTT Broker | EMQX 5.8.9 | 自带 Web 控制台看连接/主题，认证在控制台配，便于演示与排查 |
| 后端框架 | FastAPI + paho-mqtt（同进程后台线程） | 试点规模下省一个容器，分层做好后拆独立 worker 只需改入口 |
| 数据库 | PostgreSQL 16 | 表结构与连接方式可复用既有经验 |
| 大模型 | DeepSeek（v4-flash，主）+ 通义千问（备选） | 国内厂商符合合规要求，费用可控 |
| 定时任务 | APScheduler（进程内） | 与后端同进程，手动触发接口复用同一 service |
| 管理端 | Jinja2 + 原生 JS + Chart.js | 不引入独立前端工程 |
| 置信度计算 | 规则计算三档 | 保证"数据越多置信度越高"这条演示核心叙事稳定可复现，不受模型自评波动影响 |
| 原始报文归档 | 本地文件系统 `data/raw/{产线编号}/{日期}.jsonl` | 满足按产线日期分区、可重算的要求，不引入额外组件 |
| 部署 | Docker Compose 四容器一键编排 | emqx / postgres / platform / simulator |

## 快速启动

前置要求：Docker Desktop（含 Compose 插件），一份有效的 DeepSeek API Key。

```bash
# 1. 生成本地配置文件（首次部署）
python deploy/init_local.py

# 2. 一键部署：环境自检 + 构建 + 启动四容器
bash deploy/deploy.sh
```

`deploy.sh` 会依次检查 Docker 可用性、配置文件是否齐全、关键端口（1884/18084/5544/8001）是否被占用、磁盘空间、API Key 是否已填写，任一项不通过会给出明确中文错误提示并退出，不会静默失败。全部通过后启动 `docker compose up -d --build`，等待四个容器全部就绪（emqx/postgres/platform 需 healthy，simulator 需 running）。

首次部署需要初始化数据库和管理员账号：

```bash
docker compose run --rm platform python scripts/init_db.py
docker compose run --rm platform python scripts/create_admin.py
```

启动后访问：

- 管理端：http://127.0.0.1:8001
- EMQX 控制台：http://127.0.0.1:18084

清空业务数据、重新走一遍"冷启动 → 置信度提升"演示：

```bash
docker compose run --rm platform python scripts/reset_demo.py --yes
docker compose run --rm simulator python main.py --backfill-only
```

## 开发过程中发现并修复的两个真实问题

这两个问题都不是照抄能解决的机械 bug，而是新业务场景暴露了原设计没预料到的隐含假设边界：

**1. 告警事件置信度规则矛盾**

置信度算法的"时间窗口命中→high"这条路径，依赖画像分段携带 `time_windows`（作息规律）字段。但振动/温度超限告警命中的维度（振动特征/温度趋势）按设计不携带 `time_windows`，导致告警事件无论积累多少天数据，置信度永远卡在 `medium`。判断结论：超限信号本身已经足够强，不需要作息规律佐证——告警事件单独放宽为"命中天数达标即可 high"，不要求窗口匹配。

**2. 事件去重约束遗漏新场景**

真实端到端验收时发现，模拟器在一次超限读数上会同时发送 `sensor_reading` 和对应告警两条消息、共享同一个 `occurred_at`。后端原有的 QoS1 去重唯一约束 `(device_id, occurred_at)` 隐含假设"同一设备同一时刻只产生一种事件"，把后到的告警误判成重复投递直接丢弃。判断结论：约束扩展为 `(device_id, occurred_at, event_type)`——QoS1 真正的重复投递依然 100% 精确捕获，同时允许同一时刻的不同事件类型共存。修复后经真实环境重新验收，告警与读数均正常入库并各自产生下行预测。
